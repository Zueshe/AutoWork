## 1. 用户描述

按安全清单核对操作指引门户的服务端启动配置与口令处理时，发现三项相互叠加的问题：会话签发密钥有公开缺省值、口令用的是无盐快速哈希、空库会自动写入已知口令的演示管理员。单独看都是小问题，合在一起意味着**一旦生产没有设置 `SECRET`，任何能打开门户的人都可以不凭口令直接拿到管理员会话**。

## 2. 事实与证据（均已核对到具体行）

| # | 位置 | 事实 |
| --- | --- | --- |
| E1 | `server/src/index.ts:30` | `const secret = process.env.SECRET ?? 'hr-guide-dev-secret-change-me'` —— 缺省值写在源码里 |
| E2 | `server/src/index.ts:33-34` | 同一个 `secret` 既传给 `initDb`（生成种子口令哈希），又传给 `createApp`（签发/校验会话 token） |

| E4 | `server/src/auth.ts:20-21` | `verifyPassword` 用同样方式比对；调用点 `server/src/app.ts:171` |
| E5 | `server/src/app.ts:148` | token 从 `Authorization` 头读取（不校验来源之外的因素） |
| E6 | `server/src/seed.ts:7-8,15` | 演示账号 `admin@hr.example.cn / admin123`、`employee@hr.example.cn / employee123`，用 E3 的方式写库 |
| E7 | `server/src/db.ts:119` | `if (count === 0) seedDatabase(...)` —— 空库无条件灌种子 |
| E8 | `deploy/README.md` | 环境变量表**只列了 `UPLOAD_STORAGE_LIMIT_BYTES`，全文没有 `SECRET`** → 仓库里无法确认生产是否设置了它 |
| E9 | `git grep SECRET` | `SECRET` 在整个仓库的文档中零命中（只有 `JUMP_SECRET`） |

## 3. 影响

**已确认：生产未设置 `SECRET`（2026-10-18 由系统负责人确认）。以下第 1 条是当前生效的风险。**

1. **管理员会话可伪造**：用公开缺省值即可为任意 `uid` 签发合法 token，无需任何口令。可读写全部内容、上传/删除视频、改分类、查看存储用量。
2. **口令可离线恢复**：E3 无盐，相同口令哈希相同（可撞库）；HMAC 极快，拿到数据库文件后恢复口令成本很低。
3. **自动产生已知账号**：生产库一旦重建，E7 会写入 E6 的公开口令管理员。

**若生产已设置强随机 `SECRET`：** 第 1 条不成立；但第 2 条（无盐快速哈希）与第 3 条（种子账号）依然存在，对应 P2。

### 4.1 立即处置（热修复，先于代码修复）

先把口子关上，再走 §5/§6 的代码修复。

**第 0 步：确认库里有哪些账号**（决定轮换密钥会不会锁住真人）

```sh
sqlite3 /opt/hr-guide/server/data/hr-guide.db 'SELECT id, email, role FROM users;'
```

已核对代码：`users` 表只由 `server/src/seed.ts:13-15` 写入，仓库里没有任何创建用户的接口，JIRA 换票也只匹配已存在的账号。正常情况下这里应当只有两个种子账号。

**第 1 步：生成密钥并写入环境文件**

```sh
openssl rand -hex 32          # 生成后直接写入环境文件，不要贴进聊天、不要提交到仓库
# 编辑 /opt/hr-guide/hr-guide.env，增加一行：SECRET=<上一步的值>
```

**第 2 步：重启并确认服务健康**

```sh
systemctl restart hr-guide
systemctl status hr-guide --no-pager | head -5
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8787/api/auth/me   # 期望 401
```

**第 3 步：验证伪造已失效**

```sh
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer <旧缺省密钥签发的 token>" \
  http://10.42.2.141:8091/api/storage      # 期望 401（修复前是 200）
```

**轮换的副作用（务必先读）**

| 影响 | 说明 |
| --- | --- |
| 所有现有会话失效 | 用户需重新登录，符合预期 |
| **邮箱口令登录会一并失效** | `server/src/auth.ts:16` 用**同一个 `SECRET`** 计算口令哈希，换密钥后旧哈希不再匹配。第 0 步若只有种子账号，影响可忽略；若存在真人账号，须同时安排改密，或先按 §6 支持 `LEGACY_SECRET` 做兼容 |
| JIRA 跳板与账密代验不受影响 | 两条路径都不校验本地口令哈希，只需重新登录 |

## 5. 方案比较

| 方案 | 内容 | 代价 | 遗留 |
| --- | --- | --- | --- |
| A：只堵会话伪造 | 启动期校验：未设 `SECRET` 或长度不足即拒绝启动 | 最小 | 无盐口令哈希、种子账号仍在 |
| **B（推荐）** | A + 口令改用带盐 KDF（`node:crypto` 的 `scrypt`）+ 登录成功时惰性升级 + 种子账号仅显式开关下写入 | 小，集中在 `auth.ts` / `db.ts` / `seed.ts` | 无 |
| C：B + 全员强制重置口令 | 额外要求所有用户改密 | 有用户扰动 | 对本系统收益不大 |

推荐 **B**：不引入新依赖（`scrypt` 在 Node 标准库内），不要求用户改密，一次性把三类问题都封住。

## 6. 建议方案与范围

范围限 `server/` 与 `deploy/README.md`：

1. `index.ts`：`SECRET` 缺失或长度 < 32 时**快速失败**并打印明确原因（不再回退缺省值）。
2. `auth.ts`：口令哈希改为 `scrypt` + 每口令独立随机盐，格式带版本前缀（如 `scrypt$N$r$p$salt$hash`）；`verifyPassword` 兼容旧格式，成功后写回新格式。
3. `seed.ts` / `db.ts`：`NODE_ENV=production` 且未显式设置 `SEED_DEMO=1` 时不写入演示账号。
4. `deploy/README.md`：环境变量表补齐 `SECRET`（附 `openssl rand -hex 32`）与 `SEED_DEMO`。
