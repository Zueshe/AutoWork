## 1. 用户描述

排查服务端密钥问题时，在工作区里发现一个 WeKnora 的 API Key 明文写在三个启动脚本中。这三个脚本都在版本控制里，也就是说这个 Key 已经进入了 git 历史——仅仅从当前版本删掉它并不能解决问题，**必须轮换**。

## 2. 事实与证据

| # | 位置 | 事实 |
| --- | --- | --- |
| E1 | `scripts/run-backend.cmd:5` | `set "WEKNORA_API_KEY=sk-NEE3…klUU"` |
| E2 | `restart-backend.cmd:6` | 同一个 Key |
| E3 | `start-all.bat:13` | 同一个 Key |
| E4 | `git log` | 三个文件均已被跟踪并提交，Key 存在于历史提交中 |
| E5 | 根 `README.md` | 文档里写的是占位符 `<sk-开头的完整密钥>`（正确做法），说明代码与文档不一致 |

复现检查：

```sh
git grep -l "sk-NEE3"          # 命中 3 个脚本
git log --oneline -S "sk-NEE3" # 可见引入该 Key 的提交
```

## 3. 影响

- 任何能读取本仓库的人（仓库成员、历史克隆、备份、CI 日志、曾经 fork 的人）都能拿到这个 Key，直接调用内网 WeKnora 知识库接口。
- Key 权限范围取决于 WeKnora 侧配置：若含 `retrieve`/`full` 权限，可读取知识库内容；若同一 Key 复用于其他系统，影响面更大。
- 由于 Key 已在 git 历史中，**删除当前版本的文件内容不构成修复**。

## 4. 处置步骤

```sh
# 1) 在 WeKnora 侧吊销这个 Key，重新签发一个（这是唯一的真正修复）
# 2) 新 Key 只写入本地未跟踪的环境文件，例如 .env.local（确认已被 .gitignore 覆盖）
# 3) 脚本改为从环境变量读取，不再内置默认值
```

脚本改造目标（与工单 0001 已加的 `SECRET` 检查同一形式）：

```bat
if not defined WEKNORA_API_KEY (
  echo [ERROR] WEKNORA_API_KEY is not set. See .env.local.example
  exit /b 1
)
```

## 5. 验收标准

- [ ] WeKnora 侧已吊销旧 Key，并确认旧 Key 调用返回 401/403 ← **仅你能执行**
- [x] 三个脚本中不再出现 Key 明文，改为从环境变量读取（未设置时给出提示并继续，助手不可用但门户正常）
- [x] `git grep -n "sk-NEE3"` 在工作区无命中（历史提交中的残留依靠轮换失效，不做历史重写）
- [x] `.gitignore` 覆盖本地环境文件（`.env`、`.env.*`），仓库内提供 `.env.local.example`（占位值）
- [ ] 旧 Key 的吊销记录留档（谁、何时、依据）

**代码侧落点（2026-10-18）：** `.env.local.example`（新增）、`.gitignore`（补 `.env*` 规则）、`scripts/run-backend.cmd`、`restart-backend.cmd`、`start-all.bat`（移除明文 Key，改为从环境读取 `WEKNORA_API_KEY`，未设置时提示并继续）、根 `README.md`（指引到示例文件）。

## 6. 不包含

不改写 git 历史（私有仓库、单人维护，重写历史的风险大于收益，轮换即可）；不做密钥管理服务接入。

两张工单都属于"凭证与密钥"这一治理关口（设计文档 §14）。0001 修的是**会话密钥缺省值**，0002 修的是**第三方凭证入库**，可以在同一次变更里一起做完，但验收标准相互独立。
