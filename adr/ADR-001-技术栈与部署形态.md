## 1. 背景

设计文档前言明确写着「技术栈、用户规模、现有身份平台、代码平台及部署设施**尚未确认**，下文涉及选型均为建议」。也就是说本 ADR 是在**信息不完整**的条件下做决定，因此它的价值不在于选出"最好的技术"，而在于：

1. 把**可逆的决定**和**不可逆的决定**分开；
2. 给出一个**默认值**让阶段 1 能开工，同时写明什么情况下必须推翻它；
3. 明确**边界**（组件职责与禁止事项），因为设计文档 §4.1 的隔离要求比语言选择重要得多。

### 已知事实（可作为决策依据）

| # | 事实 | 来源 |

| F2 | 执行器「不持有长期凭证，也不能访问生产网络」 | 设计文档 §14.2 |

## 2. 决策驱动因素（按权重排序）

| 权重 | 因素 | 为什么排这个位置 |
| --- | --- | --- |
| 高 | **隔离边界的可表达性** | §14.2 的"执行器无长期凭证、不进生产网"是安全前提，任何方案都必须能表达 |
| 高 | **长任务与人工等待的原生支持** | §7.5.1 的计划替代、§7.8 的交接冻结都要求"事务 + 代次 + 人工等待"，自研成本极高 |
| 高 | **团队可维护性** | 平台要长期维护，语言必须是团队真的能改的 |
| 中 | 与现有设施复用度 | 复用身份/Git/CI 能省掉最容易被低估的集成工作量 |
| 中 | 落地速度 | 第一版要尽快跑通一个真实工单的闭环 |
| 中 | 审计与不可变记录的表达能力 | §14.3 要求读取也留痕、审计不可随意改写 |
| 低 | 运维成本与升级路径 | 内部平台，规模可预期 |

**可逆性判断（这一栏决定我们该多谨慎）：**

| 决定 | 可逆性 | 推翻成本 |
| --- | --- | --- |
| 语言/框架 | 低 | 约 3 个月后基本不可逆，等于重写 |
| 关系库 | 中 | DDL 与查询可迁移，运维与备份流程要重建 |
| 工作流引擎 | 中 | 状态机与补偿逻辑要重写，但业务表不受影响 |
| 对象存储 | 高 | 接口标准化，替换成本低 |
| 前端框架 | 高 | 信息架构可复用，页面重写即可 |
| 执行器隔离方式 | 中 | 涉及网络与凭证模型，晚改代价大 |

## 3. 候选方案

### 方案 A（推荐）：TypeScript 模块化单体 + PostgreSQL + Temporal + S3 兼容对象存储 + 独立执行器容器

- **语言/框架**：TypeScript，HTTP 层用 NestJS 或 Fastify（二选一由团队偏好定，不影响其余选型）
- **前端**：沿用公司主线（React 或 Vue）；原型的 13 页信息架构直接复用
- **数据库**：PostgreSQL
- **工作流**：Temporal
- **对象存储**：S3 兼容（MinIO 或公司现有）
- **执行器**：独立容器，每任务独立工作区，仅测试网段，短期令牌
- **缓存/限流**：Redis（**不**作为任务状态或审计存储）
- **检索**：先 PostgreSQL 全文检索；需要语义检索再加 pgvector

**理由**：F5/F6 显示团队已在 TypeScript 上交付过带完整测试与 CI 的系统，这是唯一有实证的可维护性依据；其余组件都直接对应 F1–F4 的形态要求。

### 方案 B：Java（Spring Boot）+ PostgreSQL + Temporal

**优点**：企业内常见，类型与事务生态成熟，招聘面广。
**代价**：与试点系统的技术栈分裂，团队要在两套工具链间切换；F5 的实证优势归零。
**适用条件**：公司已有 Java 主线与配套流水线（F7 确认）。

### 方案 C：Python（FastAPI）+ PostgreSQL + Temporal

**优点**：AI/模型生态最顺手，脚本化运维方便。
**代价**：类型契约无法与前端共享（F6 的优势消失）；大型状态机与并发部分更依赖纪律而非编译器。
**适用条件**：公司已有 Python 主线，或团队对 TS 无把握。

### 方案 D：不引入工作流引擎，用数据库状态机 + Outbox 自研

**优点**：少一个基础设施依赖与运维负担。
**代价**：§7.5.1 要求的能力要全部自己实现，且必须自己保证正确性——包括：计划替代的 CAS 与
`control_version` 串行化、重复审批决定去重、冻结与派发资格登记的竞争、在途动作清单、
迟到回调只补记历史、重启后从检查点核对真实外部状态。
**适用条件**：公司不允许引入 Temporal 这类组件，或已有等价的持久化流程平台。

## 4. 决策矩阵

对驱动因素逐项打分（●强 / ◐中 / ○弱）：

| 因素 | A（TS+Temporal） | B（Java） | C（Python） | D（自研状态机） |
| --- | --- | --- | --- | --- |
| 隔离边界可表达性 | ● | ● | ● | ● |
| 长任务/人工等待 | ● | ● | ● | ○（全靠自己实现） |
| 团队可维护性 | ●（F5 实证） | ◐（未知） | ◐（未知） | ◐ |
| 与现有设施复用 | ◐（待 F7） | ◐ | ◐ | ●（少一个组件） |
| 落地速度 | ● | ◐ | ● | ◐ |
| 审计与不可变记录 | ● | ● | ◐ | ◐ |
| 第一版实现成本 | ● | ◐ | ● | ○ |

## 5. 决策

**采用方案 A。** 若 F7 确认公司已有 Java 或 Python 主线，则**只替换语言层**（B 或 C），PostgreSQL / 工作流引擎 / 对象存储 / 执行器隔离边界**不变**——因为这些组件由设计文档的形态要求决定，与语言无关。

具体落到实现上：

| 层 | 选择 | 关键约束 |
| --- | --- | --- |
| HTTP / 业务服务 | TypeScript，模块化单体（按领域分包：工单、目录、审批、策略、分析编排） | 第一版不拆微服务 |
| 持久化 | PostgreSQL | 使用部分唯一索引与 `jsonb`，对应[领域模型 §5](../domain-model-and-stage1-api.md) |
| 工作流 | Temporal | 状态由引擎管理，**模型不得自由修改状态**（§4.1） |
| 执行器 | 独立容器，每任务独立工作区 | 无生产网络、无长期凭证、短期令牌 |
| 证据/报告存储 | S3 兼容对象存储 | 数据库只存索引、校验值与访问策略（§4.2） |
| 检索 | PostgreSQL 全文检索优先 | 检索前过滤权限，展示前再次校验（§12） |
| 缓存 | Redis（可选） | 不作为任务状态或审计存储（§4.2） |

## 6. 后果

**正面**

- 阶段 1 可以立即开工：DDL 方言确定（PostgreSQL），CI 工具链与试点系统一致（pnpm + vitest 已被验证）。
- 类型契约可前后端共享，直接套用试点项目已验证的做法（F6）。
- 工作流引擎原生覆盖 §7.5.1 / §7.7 / §7.8 的绝大部分要求，把最难的并发与恢复交给成熟组件。

**负面 / 需要接受的代价**

- **引入 Temporal 意味着一个新的基础设施依赖**，需要备份、升级与运维归属；若公司不允许，回退到方案 D 并承担自研成本。
- TypeScript 在长事务与领域建模上有语言层面的约束（需靠纪律与类型系统配合），团队要接受。
- 前端框架最终由公司主线决定，本 ADR 只承诺"信息架构复用"，不承诺代码复用。

**需要在阶段 0 内补完的**

1. Temporal 的部署形态与运维归属（自建还是复用现有平台）。
2. 对象存储与密钥管理复用哪一套（D4）。
3. 执行器的网络策略与令牌签发方式（D4）。
4. HTTP 框架在 NestJS / Fastify 之间二选一（低风险，可在迭代 1 内定）。

## 7. 明确不做的事（Non-goals）

- 第一版不拆微服务，不为每个功能建独立服务（§4.1）。
- 不自建知识库或向量检索平台；需要时再加 pgvector。
- 不把 Redis 或任何缓存当作任务状态、审计或唯一事实来源。
- 不要求 Kubernetes；仅在公司已具备时复用。
- 不在本 ADR 决定身份接入方式（属 D3）与数据分级（属 D8）。

## 8. 回退路径

| 触发条件 | 回退动作 | 代价 |
| --- | --- | --- |
| 公司不允许引入 Temporal | 切方案 D：数据库状态机 + Outbox | 必须自行实现 §7.5.1 的 CAS/代次串行化、审批去重、在途动作核对、迟到回调隔离——建议为此单独出一个 ADR 细化 |
| 公司已有 Java/Python 主线 | 替换语言层，保留其余选择 | 需重估工期；前后端类型共享的做法失效 |
| PostgreSQL 不可用 | 换关系库 | [领域模型 §5](../domain-model-and-stage1-api.md) 的 DDL 与部分索引需重写 |
| 团队规模小于 3 人 | 不换技术，缩小阶段 1 范围 | 见开发计划 §2.2 |
