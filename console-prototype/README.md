# 公司 AI 交付控制台 · 静态原型

根据《公司统一控制台与 AI 问题、需求交付平台设计方案》梳理的本地交互原型，用于评审页面结构、信息层级和从问题提交到交付验收的使用路径。

原型使用零依赖的 HTML、CSS 和经典 JavaScript 脚本，不需要安装包、构建或连接后端。

## 预览

可直接用浏览器打开本目录的 **`preview.html`**，这是包含全部样式、脚本和 13 个页面的单文件版本；也可以打开 `index.html`，它会加载同目录的源文件。

也可以在项目根目录运行本地静态服务：

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory console-prototype
```

然后打开 <http://127.0.0.1:8765>。页面内导航用于切换下面的业务路由；路由中的 `:id` 表示具体系统或工单。

修改源文件后，运行 `python3 console-prototype/build-preview.py` 更新单文件版本。主要源文件为 `styles.css`（全局视觉与响应式）、`app.js`（框架、工作台、系统与审批）、`pages-workflow.js`（工单与交付）、`pages-admin.js`（接入、工厂和试点）。

所有系统、人员、工单、审批、证据、成本和运行结果均为演示数据。页面操作仅改变原型的演示状态，不会连接真实系统、创建真实资源或执行部署。

演示状态保存在浏览器 `localStorage`，键为 `console-prototype-v1`；刷新后保留。使用页面提供的重置入口可恢复初始演示数据。不同浏览器或访问来源（例如直接打开文件与使用本地 HTTP 地址）各自保存状态。

## 页面规划

| 路由 | 页面 | 评审关注内容 |
| --- | --- | --- |
| `/home` | 工作台 | 我的待办、系统状态、近期工单和审批，帮助用户找到下一步 |
| `/systems` | 系统目录 | 按业务和状态查找系统，查看负责人、入口及接入情况 |
| `/systems/:id` | 系统详情 | 业务边界、负责人、环境版本、依赖、开放能力及相关问题 |
| `/tickets` | 工单中心 | 工单列表、分类筛选、处理状态与归属，区分等待和阻塞 |
| `/tickets/new` | 提交问题 | 系统或“暂不确定”、问题类型、场景、影响、复现及上下文采集范围 |
| `/tickets/:id` | 工单详情 | 用户描述、公开摘要、讨论、时间线、责任人及业务验收 |
| `/tickets/:id/analysis` | 分析与方案 | 事实与假设、引用证据、方案比较、验收标准、范围、风险与计划版本 |
| `/approvals` | 审批中心 | 待办及决定，核对审批类型、对象版本、差异和批准范围 |
| `/executions` | 执行监控 | 执行步骤、检查点、测试证据、耗时成本、阻塞及人工接管 |
| `/releases` | 发布与验收 | 候选制品、目标环境、发布条件、观察、恢复及业务验收 |
| `/integrations` | 系统接入 | 清单版本、连接器健康、能力与环境授权、接入检查 |
| `/factory` | 新系统交付 | 业务与数据边界、模板资源、阶段产物、运行准备及目录激活 |
| `/pilot` | 试点评估 | 样本与准入、人工基线、统计分母、总成本、门槛与阶段决定 |

执行步骤、审批证据和接入检查可在所属页面中展开查看，无须为每个步骤增加独立导航。工单的“已关闭”、执行的“成功”和发布后的“观察通过”应分别表达，避免将技术完成误读为业务验收完成。

## 按角色查看

| 角色 | 优先关注页面 | 要确认的问题 |
| --- | --- | --- |
| 普通提交人 | 工作台、提交问题、工单中心、工单详情 | 是否容易提交、知道谁在处理、补充信息并确认结果 |
| 业务负责人 | 分析与方案、审批中心、发布与验收、试点评估 | 目标、范围、收益和验收是否清楚，交付是否解决实际问题 |
| 技术负责人 | 系统详情、分析与方案、执行监控、系统接入 | 证据与判断是否对应，影响范围、验证和接管信息是否充分 |
| 发布及运行维护负责人 | 执行监控、发布与验收、系统详情 | 实际发布对象、环境、观察指标和恢复方式是否可核对 |
| 平台管理员 | 系统目录、系统接入、新系统交付、试点评估 | 能力授权、接入健康、资源归属和阶段门槛是否可管理 |

角色划分用于评审各类用户的信息需求；真实身份认证、后端权限校验及数据隔离需要在正式系统中实现。

## 推荐演示路径

1. **现有系统 Bug 闭环：** 从工作台进入工单，查看用户描述和证据，再进入分析与方案，核对计划及验收版本；随后查看审批、执行步骤、测试结果、发布观察和业务验收。重点确认每一步的下一责任人和下一动作是否明确。
2. **执行阻塞与接管：** 在执行监控中查看异常步骤，核对已经发生的动作、外部状态、交接信息和后续处理路径；再回到工单，检查用户能否理解当前进度。
3. **新需求与系统交付：** 先在系统目录确认现有能力，再从提交问题进入方案比较；选择新系统场景后查看新系统交付页中的边界、资源、阶段产物及激活条件，并核对相应审批和发布验收。
4. **试点是否扩大：** 进入试点评估，分别查看历史回放与真实工单结果，核对样本、失败及转人工的统计方式、审核返工工时和模型执行成本，最后评审继续、扩大、缩小或暂停的依据。

评审前可重置演示状态，使不同参与者从同一组数据和状态开始。
